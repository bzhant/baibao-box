# 白的百宝箱 · Baibao Box

**面向日 / 英游戏的汉化工具箱 —— 拖进来，点一下，能读了。**

[![许可证](https://img.shields.io/badge/许可证-MIT-blue.svg)](./LICENSE)

一个 Windows 桌面工具：**选游戏目录 → 点一下 → 游戏里的文字就是中文**。

- **一键汉化（运行时）** —— 不改游戏数据文件，边玩边翻，关掉游戏自动逐字节还原；
  数据被加密的游戏同样有效。目前覆盖 RPG Maker MV / MZ。
- **静态汉化** —— 把译文写进游戏数据文件，**一次改完永久生效**、之后离线可玩不依赖本程序。
  覆盖 MV / MZ / Ren'Py。

## 核心特性

| 特性 | 说明 |
|---|---|
| **一键汉化并启动**（运行时） | 选游戏目录 → 点一下 → 游戏启动**已经是中文**。**不改游戏数据文件**，数据被加密的游戏同样有效；**关闭游戏即自动逐字节还原**。译文走你配置的接口，并本地积累成译文库 |
| **一键汉化**（静态改文件） | 选游戏目录 → 确认选项 → 开始。译文**落进游戏数据文件**，之后离线可玩、不依赖本程序运行 |
| **控制符保护** | 翻译前把 `\C[1]` `\V[3]` 这类控制符扣出来占位，翻完装回；装不回去的**拒绝写回**而不是带着错误写进游戏 |
| **翻译记忆 + 术语表** | 同游戏二次运行不重复送翻；人名地名固定译法，不会出现一个角色三个名字 |
| **人工修订工作台** | 按文件浏览 / 搜索 / 状态筛选 / 单条编辑 / 批量替换（**先预演给样例**）/ 导入导出 / 覆盖率 |
| **只回写** | 工作台改完直接落进游戏，**不必重跑整条流水线** |
| **一键还原** | 所有改动自动备份，还原后**逐字节一致**（每次交付前都在真实游戏上验证） |
| **双插件架构** | 引擎适配器（能读什么游戏）× 翻译 Provider（用什么翻），均热插拔 |
| **接口方案可存多套** | DeepSeek / OpenAI / 本地 Ollama / 自定义（OpenAI 兼容）各存一套，随时切换；每套各存各的密钥。内置**「测试连接」**：真发一句试出来，而不是翻到一半才炸 |
| **本地优先** | 翻译记忆、术语表、文本库全在本机；除你自己配置的机翻接口外**没有任何数据外发** |

| 引擎 | 静态汉化 | 一键汉化（运行时） | 说明 |

| **RPG Maker MV** | ✅ | ✅ | 真实游戏实测抽出 **4064** 条文本，控制符零损失 |
| **RPG Maker MZ** | ✅ | ✅ | 真实游戏实测抽出 **7487** 条文本 |
| **Ren'Py** | ✅ | ⏳ | `.rpy` 字符串感知解析 + 原地回写；运行时桥待做 |

| KiriKiri | ❌ | ❌ | 无可用真样本、无法验证，已移出计划 |

> **原则：没有真样本就无法验证，无法验证就不叫"支持"。** 上表只列真的测过的。
>

## 使用

### 方式一（推荐）：一键汉化并启动 · 运行时

**① 选游戏目录** —— 选完**立刻**识别引擎，选错目录马上就知道。

**② 点「一键汉化并启动」** —— 游戏会启动，**里面的文字已经是中文**。

- **不改游戏数据文件。** 全部改动只有两处：`plugins.js` 里加一行注册 + 放一个桥插件；
  **关掉游戏就自动逐字节还原**（改前备份 + SHA-256 校验）。
- **数据被加密的游戏同样有效** —— 静态路线读不出被加密的数据，运行时**根本不读它**。
- **边玩边翻。** 游戏进程里的桥在真实绘制入口取词，宿主用你配置的翻译接口回译文；
  界面上实时显示「取词 N 条 / 本地命中 N / 接口得译文 N」。
- **翻译不重复花钱。** 命中的句子直接走本地**译文库**，没命中才调接口，结果回写译文库。
  游戏目录里若已有 `{原文: 译文}` 形式的中文字典，会**自动导入**当预置译文。
- 目前支持 **RPG Maker MV / MZ**；其它引擎请用方式二。

> 未配置翻译接口密钥时，界面会**明确告诉你**当前用的是"本地假机翻"（译文形如 `【中】原文`），
> 它只用于验证流程，**不是真翻译**。

### 先配一个翻译接口（一次性）

「配置」页 → **翻译接口方案** → 从预置里挑一个新建（内置 **DeepSeek**，地址与模型已填好）→
粘上密钥 → 点**「测试连接」**（会真发一句「こんにちは」去试，几秒内就知道通不通）→ 保存。

可以存多套（DeepSeek / OpenAI / 本地 Ollama / 中转站）随时切换 —— 不同游戏文本量不同，
"哪家便宜用哪家"；换方案不用重新粘密钥。**没配密钥时会用"本地假机翻"**（译文形如 `【中】原文`），
只用于验证流程，不是真翻译。

### 方式二：静态汉化 · 改游戏数据文件

**① 选游戏目录** —— 同上，选完立刻识别引擎。

**② 确认选项** —— 源语言 / 目标语言 / 是否注入中文字体 / 是否先试译一小段。

**③ 开始汉化** —— 阶段化进度（抽取 → 入库 → 查翻译记忆 → 翻译 → 回写 → 注入字体），
完成后给出明细：抽取 / 新入库 / 翻译成功 / **控制符冲突**（已拒绝写回）/ 失败。

译文**落进游戏数据文件**，之后**离线可玩、不依赖本程序运行**；想改回来随时「一键还原」。

### 命令行

打包后的可执行文件支持 headless 模式，适合批处理：

```bash
# 一键汉化并启动（运行时，推荐）
白的百宝箱.exe --runtime "D://games//某游戏"

# 万一它被强杀（断电 / 任务管理器），用这条把游戏目录收干净
白的百宝箱.exe --runtime-restore "D://games//某游戏"

# 静态汉化：先试译 30 条看看效果
白的百宝箱.exe --game "D://games//某游戏" --limit 30

# 只抽取入库、不回写（先检查抽得准不准）
白的百宝箱.exe --game "D://games//某游戏" --no-repack

# 完整跑一遍
白的百宝箱.exe --game "D://games//某游戏"

# 只回写（工作台改完之后，不必重跑流水线）
白的百宝箱.exe --game "D://games//某游戏" --repack-only

# 一键还原（静态汉化的改动）
白的百宝箱.exe --game "D://games//某游戏" --restore

白的百宝箱.exe --help
```

## 工作原理

### 架构

```
┌──────────────────────────────────────────────────────────────────┐
│  Renderer (React)          汉化 / 工作台 / 配置 / 日志            │
└──────────────────────────────┬───────────────────────────────────┘
                               │ 白名单 IPC（不暴露 ipcRenderer）
┌──────────────────────────────▼───────────────────────────────────┐
│  Main (Electron)                                                  │
│   ├─ translate-service    静态编排（命令行与界面**共用同一套**）    │
│   ├─ runtime-service      一键汉化编排（同上，命令行与界面共用）     │
│   ├─ workbench-service    人工修订的数据操作                       │
│   ├─ config / logbus      配置（密钥加密存储）/ 内存日志总线         │
│   └─ pipeline             抽取 → 入库 → 查 TM → 翻译 → 回写 → 字体  │
└──┬──────────────────────┬───────────────────────┬────────────────┘
   │                      │                       │
┌──▼──────────┐  ┌────────▼──────────┐  ┌─────────▼─────────────────┐
│ 引擎适配器   │  │ 翻译 Provider      │  │ host/runtime（运行时）     │
│ mvmz / renpy│  │ OpenAI 兼容 / stub │  │ 总线 · 译文库 · 可逆激活器  │
└──┬──────────┘  └───────────────────┘  └─────────┬─────────────────┘
   │                                              │ 本地 WebSocket
┌──▼──────────────────────────────────────────┐   │ 127.0.0.1（端口探测）
│ 平台层：文本库(SQLite+FTS5) / 通用补丁        │   │
│ （按字节备份 · 清单 · 倒序还原）              │   ▼
└─────────────────────────────────────────────┘  ┌───────────────────┐
                                                 │ 游戏进程内的运行时桥│
                                                 │ 取词 → 回填 → 还原 │
                                                 └───────────────────┘
```

### 两条路怎么选

| | 一键汉化（运行时） | 静态汉化（改数据文件） |
|---|---|---|
| 改游戏文件 | 只加一行注册 + 一个插件，**退出即还原** | 译文写进 `data/*.json` 等数据文件 |
| 数据被加密 | ✅ 有效（运行时根本不读它） | ❌ 读不出来 |
| 游戏关掉之后 | 回到原文 | **中文保留**（离线可玩、不依赖本程序） |
| 需要本程序运行 | 是（边玩边翻） | 否 |
| 适合 | 先玩起来 / 加密游戏 / 不想动游戏文件 | 想一次改完永久生效，之后脱离工具玩 |
| 覆盖引擎 | MV / MZ | MV / MZ / Ren'Py |

**为什么静态路线这一层还在**：MV/MZ 跑在 NW.js 上、游戏逻辑是**明文 JavaScript**，文本在明文 JSON 里；
Ren'Py 跑在 Python 上、脚本明文且自带翻译机制。对这类游戏，"改文件"能做到"注入"能做的一切，
却天然规避了注入的全部风险（进程崩溃、杀软误报、位数不匹配、卸载不干净）。想"改一次永久生效"时它更合适。

**为什么现在把运行时放到推荐位**：加密数据、运行期才算出来的文本，静态路线读不到；
而且运行时**根本不动游戏数据**，玩家随时能"关掉工具回到原样"。
两条路**共用同一套翻译 Provider 与配置**；静态工作台和运行时各自维护适合其访问模式的本地缓存。

### 一键汉化（运行时）是怎么工作的

```
宿主（本程序）                                    游戏进程里的「运行时桥」
 ├─ 起总线（仅回环 127.0.0.1，端口探测+接头文件）   ┌────────────────────────────┐
 ├─ 把桥**可逆地**装进游戏（MV/MZ：                │ 挂在真实绘制入口上          │
 │   plugins.js 加一行注册 + 放一个插件文件）       │ 遇到没见过的原文 → 登记待译  │
 ├─ 启动游戏 ────────────────────────────────────▶ │ 译文进缓存 → 下次绘制换中文  │
 └─ 应答取词请求（接在同一条翻译能力上）            └────────────────────────────┘
        ▲                                                    │
        └────────── 取词(原文) / 译文 ←───────────────────────┘
                    本地 WebSocket（只走回环）
```

**引擎侧的拦截点在哪，取决于引擎**：

- **MV / MZ**：文本全程在 JS 里（NW.js），**编码层 hook 在这类引擎上看不见任何东西**，
  所以拦截点挂在 JS 的真实绘制入口（`Window_Base.prototype.drawText`），
  装法是"**可逆地装一个插件**"，而不是注入 DLL；
- **老 galgame 那类**（文本经原生文本 API 画出来）：才用编码层 DLL hook。
  这一层已经打通并在玩具目标上验证过 —— 等真正遇到那类引擎再接。
  **同一个宿主会话服务两类**，不用写两套总线与翻译调度。

三条设计约束，都是这类工具翻车的常见地方：

- **游戏线程绝不等待网络** —— 未命中就登记一句、本帧原样放行，绝不把"等宿主回话"塞进被 hook 的 API；
- **同一句只问一次** —— 否则每帧都问一遍，宿主被刷爆；
- **宿主不在就自己停下来** —— 连续无应答即停用运行时取词，游戏照常玩、本地词表照常工作。

**译文一到就立刻刷新文本窗口**（不是等下一次自然重绘）—— 否则遇到标题界面这类长时间不重绘的
静态画面，译文到了却迟迟不显示（这是实测踩到的，不是理论问题）。

译文不重复花钱：命中**译文库**就直接用（本地缓存 + 会自动导入游戏目录里已有的
`{原文: 译文}` 字典文件），没命中才调接口，拿到的结果回写译文库。
实测差距很明显（同一个真实 MV 游戏）：

| 场景 | 到"游戏里真的显示中文" |
|---|---|
| 首次（冷缓存，要调接口） | ~219 秒（其中绝大多数是那个游戏自身加载慢：3.4 GB / 140+ 插件） |
| 第二次（命中译文库） | **6 秒** |

> **现状**：MV/MZ 这条线已在**真实游戏**上端到端验证 ——
> `src/main/runtime-service.test.ts`：文本真的被换成译文（以桥自述 `apply>0` 为证，不看截图）→
> 收尾后 `plugins.js` 逐字节还原 → 第二次启动命中译文库。

### 排版回填：两代引擎做法相反

日文换中文后字符宽度变化，原本一行放得下的句子会溢出。实测结论：

| 引擎 | 实测每行容量 | 处理方式 |
|---|---|---|
| MV | 25.2 全角字（contents 604px / 字号 24） | MV/MZ **原版没有横向自动折行** → 由本项目补上，含中文标点**避头尾规则** |
| MZ | 71.9 全角字（contents 1868px / 字号 26） | 同上；消息窗满宽，风险主要在**窄窗** |
| Ren'Py | 引擎自带 | **不需要**处理 —— Ren'Py 有专业排版引擎与 CJK 断行（`style.language`） |

> 这三个数字都是**在真实游戏进程中实测**得到的，不是按引擎默认值推导的
> （MV 实测屏幕 1400×950 而非默认 816×624、字号 24 而非 28 —— 推导会全错）。

### 字体：不分发字体文件

中文显示成方块是因为游戏字体没有汉字。本项目让引擎去用**系统里已有的中文字体**，
**不向游戏目录写入任何字体文件**（涉及授权）：

- **MV**：改 `System.json` 的 `locale`
- **MZ**：改 `advanced.fallbackFonts`
- **Ren'Py**：`FontGroup` 给 CJK 加回退，**保留游戏原有装饰字体**

## 工程原则

**① 一切可逆。**
任何修改游戏文件的操作都先自动备份；补丁按倒序展开还原。
"还原后逐字节一致"是每次交付前在真实游戏上验证过的断言，不是口头保证。

**② 不静默外发数据。**
翻译记忆、术语表、文本库全在本机。除用户自己配置的翻译接口外，
没有任何字节离开本机 —— 未配置密钥时使用**本地假机翻**，而不是悄悄上传。

**③ 不实现任何反检测 / 不绕过杀软。**
项目解决的是"看不懂"，不是"绕过什么"。

- 存档管理 / 游戏修改器 / 悬浮翻译 / 封面识别 / 地图导出
- 应用图标与代码签名
- Unity 适配（资源解析已就绪，对象枚举待完成）

  回填发生在目标进程内部，所以断言的是日志里的结构化自述行，**不需要人看窗口**

## 已知限制

- **真翻译需要配置翻译接口密钥**；未配置时使用本地假机翻，仅用于验证流程。
- **数据被加密的游戏无法处理**（部分游戏会加密自身数据文件）。此时会被**明确拒绝**并说明原因，
  而不是把文件改坏。处理这类游戏需要运行时提取能力，属后续工作。
- **MZ 插件指令文本**（写在插件参数中的文本）尚未覆盖。
- **没有应用图标**（当前使用 Electron 默认图标）、**没有代码签名**。
- **运行时汉化目前只覆盖 MV / MZ**（这两代占了目标游戏的绝大多数）。
  它是把桥**可逆地装进游戏**（改 `plugins.js`、退出时逐字节还原），
  还不是"注入 DLL"那种形态 —— 后者留给静态路线彻底走不通的引擎。
- **运行时汉化需要本程序在运行**（关掉游戏就收尾还原）；想要"改一次永久生效"请用静态汉化。

## 开发

### 环境要求

| 项 | 版本 |
|---|---|
| Node.js | ≥ 22（推荐 22 LTS） |
| Windows | 10 / 11 x64 |
| MSVC Build Tools | 编译 `better-sqlite3` 需要 |

### 常用命令

```bash
npm run dev        # 开发模式起窗（热更新）
npm test           # 单元测试（自动处理原生模块 ABI）
npm run typecheck  # 类型检查
npm run lint       # TypeScript 严格检查
npm run build      # 编译三进程产物
npm run check      # 类型检查 + 全量测试 + 构建
npm run dist       # 打包：NSIS 安装包 + 免安装版
npm run e2e        # Electron 起窗 + SQLite/渲染层端到端冒烟
```

> **原生模块 ABI 提示**：`better-sqlite3` 在 Node 与 Electron 下 ABI 不同。
> `npm test` 会自动切到 Node ABI，打包 / 运行时需要 Electron ABI
> —— 跑完测试想开应用，先执行 `npm run rebuild:electron`。

### 项目结构

```
src/
├─ shared/         接口契约（EngineAdapter / EngineManifest / TextEntry …）
├─ platform/       基础设施：插件注册表 / 文本库 / 补丁 / 配置 / 日志
├─ text-kernel/    文本内核：控制符 token 化 / 抽取 / 回写
├─ engines/        引擎适配器插件（mvmz / renpy）+ 各自 runtime
├─ translate/      翻译 Provider 插件 + 术语表 + 质量自检
├─ pipeline/       流水线编排
├─ main/           主进程：服务层 / IPC 白名单 / CLI
├─ preload/        渲染层 API 白名单
└─ renderer/       界面（React）
```

### 新增一个引擎

1. 在 `src/engines/<id>/` 实现 `EngineAdapter`（`detect` / `extract` / `repack`）；
2. 填一份 **`EngineManifest`** —— 该选哪层目录、常见源语言、字体机制、已知坑；
3. 注册到 `src/main/bootstrap-plugins.ts`。

**界面无需改动** —— 界面只读 manifest 数据，不含任何 `if (engineId === 'xxx')` 分支。

## 核心特性

| 特性 | 说明 |
|---|---|
| **一键汉化** | 选游戏目录 → 确认选项 → 开始。对白、旁白、选项、道具说明、技能描述、角色名全覆盖 |
| **控制符保护** | 翻译前把 `\C[1]` `\V[3]` 这类控制符扣出来占位，翻完装回；装不回去的**拒绝写回**而不是带着错误写进游戏 |
| **翻译记忆 + 术语表** | 同游戏二次运行不重复送翻；人名地名固定译法，不会出现一个角色三个名字 |
| **人工修订工作台** | 按文件浏览 / 搜索 / 状态筛选 / 单条编辑 / 批量替换（**先预演给样例**）/ 导入导出 / 覆盖率 |
| **只回写** | 工作台改完直接落进游戏，**不必重跑整条流水线** |
| **一键还原** | 所有改动自动备份，还原后**逐字节一致**（每次交付前都在真实游戏上验证） |
| **双插件架构** | 引擎适配器（能读什么游戏）× 翻译 Provider（用什么翻），均热插拔 |
| **本地优先** | 翻译记忆、术语表、文本库全在本机；除你自己配置的机翻接口外**没有任何数据外发** |

## 支持的引擎

| 引擎 | 状态 | 说明 |
|---|---|---|
| **RPG Maker MV** | ✅ 可用 | 真实游戏实测抽出 **4064** 条文本，控制符零损失 |
| **RPG Maker MZ** | ✅ 可用 | 真实游戏实测抽出 **7487** 条文本 |
| **Ren'Py** | ✅ 可用 | `.rpy` 字符串感知解析 + 原地回写 |
| Unity | ⏳ 后续版本 | 资源容器解析（UnityFS / SerializedFile）已就绪，对象枚举未完成，本版本不投入 |
| KiriKiri | ❌ 不支持 | 无可用真样本、无法验证，已移出计划 |

> **原则：没有真样本就无法验证，无法验证就不叫"支持"。** 上表只列真的测过的。
>
> 兼容性由**引擎适配器**承担，新增引擎不需要改动界面 —— 见 [`EngineManifest`](./src/shared/contracts.ts)。

## 快速开始

### 使用（安装包）

从 [Releases](https://github.com/bzhant/baibao-box/releases) 下载：

| 文件 | 说明 |
|---|---|
| `baibao-box-0.1.0-portable.exe` | **免安装版**（portable），双击即用 |
| `baibao-box-0.1.0-setup.exe` | NSIS 安装包，可选安装目录 |

> ⚠️ 尚未做代码签名，Windows 首次运行会弹 SmartScreen 警告，选择"仍要运行"即可。

```bash
git clone <repo> && cd baibao-box
npm install     # 含 better-sqlite3 原生编译
npm run dev     # 开发模式起窗
```

## 使用

### 图形界面：三步

**① 选游戏目录** —— 选完**立刻**识别引擎，选错目录马上就能知道，不用等跑完一轮才发现。

**② 确认选项** —— 源语言 / 目标语言 / 是否注入中文字体 / 是否先试译一小段。

> 未配置翻译接口密钥时，界面会**明确告诉你**当前用的是"本地假机翻"
> （译文形如 `【中】原文`），它只用于验证流程，**不是真翻译**。

**③ 开始汉化** —— 阶段化进度（抽取 → 入库 → 查翻译记忆 → 翻译 → 回写 → 注入字体），
完成后给出明细：抽取 / 新入库 / 翻译成功 / **控制符冲突**（已拒绝写回）/ 失败。

### 命令行

打包后的可执行文件支持 headless 模式，适合批处理：

```bash
# 先试译 30 条看看效果
白的百宝箱.exe --game "D:\games\某游戏" --limit 30

# 只抽取入库、不回写（先检查抽得准不准）
白的百宝箱.exe --game "D:\games\某游戏" --no-repack

# 完整跑一遍
白的百宝箱.exe --game "D:\games\某游戏"

# 只回写（工作台改完之后，不必重跑流水线）
白的百宝箱.exe --game "D:\games\某游戏" --repack-only

# 一键还原
白的百宝箱.exe --game "D:\games\某游戏" --restore

白的百宝箱.exe --help
```

## 工作原理

### 架构

```
┌──────────────────────────────────────────────────────────────┐
│  Renderer (React)        汉化 / 工作台 / 配置 / 日志          │
└───────────────────────────┬──────────────────────────────────┘
                            │ 白名单 IPC（不暴露 ipcRenderer）
┌───────────────────────────▼──────────────────────────────────┐
│  Main (Electron)                                              │
│   ├─ translate-service   编排（CLI 与界面**共用同一套**）      │
│   ├─ workbench-service   人工修订的数据操作                    │
│   ├─ config / logbus     配置（密钥加密存储）/ 内存日志总线      │
│   └─ pipeline            抽取 → 入库 → 查 TM → 翻译 → 回写 → 字体│
└───────┬───────────────────────────────────┬──────────────────┘
        │                                   │
┌───────▼─────────┐               ┌─────────▼─────────────────┐
│ 引擎适配器插件   │               │ 翻译 Provider 插件         │
│ mvmz / renpy    │               │ OpenAI 兼容 / stub        │
│ + EngineManifest│               │ (可插拔)                   │
└───────┬─────────┘               └───────────────────────────┘
        │
┌───────▼──────────────────────────────────────────────────────┐
│  平台层：文本库(SQLite+FTS5) / 通用补丁(备份·清单·倒序还原)     │
└──────────────────────────────────────────────────────────────┘
```

### 为什么是"静态改文件"而不是"进程注入"

汉化这类游戏有两条路：把 DLL 注入游戏进程改内存，或者解析游戏数据文件、改为译文再写回。

**本项目走第二条。** 依据是游戏本身的构造：

- RPG Maker MV / MZ 跑在 NW.js 上，游戏逻辑是**明文 JavaScript**，文本在明文 JSON 里；
- Ren'Py 跑在 Python 上，脚本明文，且**自带翻译机制**。

对这类游戏，"改文件"能做到"注入"能做的一切，却天然规避了注入的全部风险：
进程崩溃、杀软误报、32/64 位不匹配、卸载不干净。

> 注入留给真正啃不动的引擎 —— 那时它才是**必需**的，而不是第一选择。

### 运行时注入：静态路线走不通时的那条路

数据被加密、脚本被编译（`.scn`）、资源被打包（UnityFS）的游戏，静态读不出文本，
只能在其**运行时**取词。这条链路已经打通到「**宿主驱动 → 运行时取词 → 翻译 → 回填**」：

```
宿主（本程序）
 ├─ 起总线 —— 原生侧要连的接头地点（端口探测 + 接头文件，不写死端口）
 ├─ 用注入器把 hook 带进游戏进程（挂起启动 → 注入 → 恢复执行，全程可卸载）
 └─ 应答取词请求 —— 接在同一条翻译流水线上
        ▲                              │
        │ translate(原文)               │ 译文
        │                              ▼
游戏进程里的 hook：热路径遇到词表外的原文 → 登记待译 → 译文进缓存 → 下一帧就渲染成中文
```

三条设计约束，都是这类工具翻车的常见地方：

- **游戏线程绝不等待网络** —— 未命中就登记一句、本帧原样放行，绝不把"等宿主回话"塞进被 hook 的 API；
- **同一句只问一次** —— 否则每帧都问一遍，宿主被刷爆；
- **宿主不在就自己停下来** —— 连续无应答即停用运行时取词，游戏与本地词表完全不受影响。

> **现状**：宿主 ↔ 原生这条链已用**玩具目标**端到端验证
> （`npm test` 里的 `src/host/runtime/runtime-inject.test.ts`，含阴性对照）。
> 面向真实引擎的 hook DLL 是下一步 —— 按项目规矩，**每个 hook 上真游戏前必须先过玩具目标**。

### 排版回填：两代引擎做法相反

日文换中文后字符宽度变化，原本一行放得下的句子会溢出。实测结论：

| 引擎 | 实测每行容量 | 处理方式 |
|---|---|---|
| MV | 25.2 全角字（contents 604px / 字号 24） | MV/MZ **原版没有横向自动折行** → 由本项目补上，含中文标点**避头尾规则** |
| MZ | 71.9 全角字（contents 1868px / 字号 26） | 同上；消息窗满宽，风险主要在**窄窗** |
| Ren'Py | 引擎自带 | **不需要**处理 —— Ren'Py 有专业排版引擎与 CJK 断行（`style.language`） |

> 这三个数字都是**在真实游戏进程中实测**得到的，不是按引擎默认值推导的
> （MV 实测屏幕 1400×950 而非默认 816×624、字号 24 而非 28 —— 推导会全错）。

### 字体：不分发字体文件

中文显示成方块是因为游戏字体没有汉字。本项目让引擎去用**系统里已有的中文字体**，
**不向游戏目录写入任何字体文件**（涉及授权）：

- **MV**：改 `System.json` 的 `locale`
- **MZ**：改 `advanced.fallbackFonts`
- **Ren'Py**：`FontGroup` 给 CJK 加回退，**保留游戏原有装饰字体**

## 工程原则

**① 一切可逆。**
任何修改游戏文件的操作都先自动备份；补丁按倒序展开还原。
"还原后逐字节一致"是每次交付前在真实游戏上验证过的断言，不是口头保证。

**② 不静默外发数据。**
翻译记忆、术语表、文本库全在本机。除用户自己配置的翻译接口外，
没有任何字节离开本机 —— 未配置密钥时使用**本地假机翻**，而不是悄悄上传。

**③ 不实现任何反检测 / 不绕过杀软。**
项目解决的是"看不懂"，不是"绕过什么"。

## 已知限制

- **真翻译需要配置翻译接口密钥**；未配置时使用本地假机翻，仅用于验证流程。
- **数据被加密的游戏无法处理**（部分游戏会加密自身数据文件）。此时会被**明确拒绝**并说明原因，
  而不是把文件改坏。处理这类游戏需要运行时提取能力，属后续工作。
- **MZ 插件指令文本**（写在插件参数中的文本）尚未覆盖。
- **没有应用图标**（当前使用 Electron 默认图标）、**没有代码签名**。
- **运行时注入目前只有"玩具目标"的 hook**：宿主 ↔ 原生这条链已打通并验证，
  但面向某一真实引擎的 hook DLL 还没写（按项目规矩，每个 hook 都必须先过玩具目标）。
  也因此界面上还没有运行时模式的入口。

## 开发

### 环境要求

| 项 | 版本 |
|---|---|
| Node.js | ≥ 22（推荐 22 LTS） |
| Windows | 10 / 11 x64 |
| MSVC Build Tools | 编译 `better-sqlite3` 需要 |

### 常用命令

```bash
npm run dev        # 开发模式起窗（热更新）
npm test           # 单元测试（自动处理原生模块 ABI）
npm run typecheck  # 类型检查
npm run lint       # 代码检查（ESLint）
npm run build      # 编译三进程产物
npm run dist       # 打包：NSIS 安装包 + 免安装版
npm run smoke      # 冒烟：起窗 + 平台层自检 + 退出
```

> **原生模块 ABI 提示**：`better-sqlite3` 在 Node 与 Electron 下 ABI 不同。
> `npm test` 会自动切到 Node ABI，打包 / 运行时需要 Electron ABI
> —— 跑完测试想开应用，先执行 `npm run rebuild:electron`。

### 项目结构

```
src/
├─ shared/         接口契约（EngineAdapter / EngineManifest / TextEntry …）
├─ platform/       基础设施：插件注册表 / 文本库 / 补丁 / 配置 / 日志
├─ text-kernel/    文本内核：控制符 token 化 / 抽取 / 回写
├─ engines/        引擎适配器插件（mvmz / renpy）+ 各自 runtime
├─ translate/      翻译 Provider 插件 + 术语表 + 质量自检
├─ pipeline/       流水线编排
├─ main/           主进程：服务层 / IPC 白名单 / CLI
├─ preload/        渲染层 API 白名单
└─ renderer/       界面（React）
```

### 新增一个引擎

1. 在 `src/engines/<id>/` 实现 `EngineAdapter`（`detect` / `extract` / `repack`）；
2. 填一份 **`EngineManifest`** —— 该选哪层目录、常见源语言、字体机制、已知坑；
3. 注册到 `src/main/bootstrap-plugins.ts`。

**界面无需改动** —— 界面只读 manifest 数据，不含任何 `if (engineId === 'xxx')` 分支。

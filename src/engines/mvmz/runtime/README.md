# MV 运行时适配

RPG Maker MV 的**运行时**插件。与 `src/engines/mvmz/` 的 TS 侧分工不同：

| 层 | 位置 | 干什么 | 时机 |
|---|---|---|---|
| 数据层（离线） | `src/engines/mvmz/` | 抽取/翻译/回写 `data/*.json`、改 `System.json` 的 `locale` | 汉化时 |
| **运行时层** | 本目录 + `tools/mv-runtime/` | 补上引擎**本来没有**的横向折行 | 游戏运行时 |

## 为什么 MV 需要运行时插件

先侦察再写码，侦察结论（详见 `docs/recon/MV-引擎侦察报告.md`）：

- **MV 原版没有横向自动折行** —— `Window_Base.processNormalCharacter` 只做
  `textState.x += w`，没有任何宽度判断；`needsNewPage` 只判垂直；全文件无折行代码。
  视觉换行来自数据结构（`Game_Message.allText = _texts.join('\n')`）。
- 该游戏装了唯一提供折行的插件 YEP_MessageCore，但**三重关闭**：参数 `Word Wrapping=false`、
  数据里 0 处 `<WordWrap>` 标签、且它的实现只在"下个字符是空格"时才计算宽度（**对 CJK 恒为 false**）。
- **实测**（`tools/mv-runtime/BB_Probe.js` 在真机上跑出来的）：
  `contents.width = 604px`、`fontSize = 24px`、每字 24px ⇒ **每行只能放 25 个全角字**。
  原文自身就有 **7.2%** 的对白超过这个宽度（已排除走战斗日志的 `_ABL` 行）。

## 交付物

### `BB_Layout.js` —— 排版回填插件（引擎无关的通用版）

- **拦截点**：`Window_Base.prototype.processCharacter`
  理由：它是所有多行文本的必经之路；宽度信息就在手边（`textState.x` / `textState.left` /
  `this.contents.width`）——**按窗口取宽度**，不用全局常量（各窗口宽窄不同）。
- **★ 换行怎么插进去（最容易做错的一步）**：
  不能直接调 `processNewLine` —— 它内部有 `textState.index++`，那是为"消费掉那个 `\n`"
  设计的。中文没有空格可供消费，直接调会把**当前这个字**吃掉，导致**丢字**。
  （YEP 只在中英"空格处"折行，正好用 `index++` 抵掉空格，所以它没暴露这个问题。）
  正确做法：**往 `textState.text` 里插一个真的 `'\n'`**，原 `processCharacter` 会看到它
  并走 `processNewLine`。字符一个不多、一个不少。
- **中文禁则**：行首禁则（`，。、；：？！）】》」』…—` 不出现在行首）+
  行尾禁则（`（【《「『` 不出现在行尾）。用**前瞻**实现：判断到"下一个字是不能放行首的标点
  且它放不下本行"时，把当前字一起挪下去 —— 避免"把标点孤零零留在行首"。
- **一键还原**：插件命令 `BBLayout off`（或 `BB_Layout.setEnabled(false)`）之后
  **一行都不折**，与未装插件时完全一致。

### 只在**绘制时**折行，不往数据里插换行

离线往 JSON 里插 `\n` 看起来更省事，但：离线时不知道运行时的窗口宽度与字体（改 `locale`
会换字体，宽度随之变）；同一段文本在不同窗口宽度不同；插进去的 `\n` 会污染存档/日志/
其它插件。**参考实现里也没这么做**（实测第三方样本 59854 条翻译里 `\n` 插入数为 0）。

### 明确**不做**的：字号自适应

折行只解决横向；纵向（行数超过窗口可见行数）会触发分页。实测这一层几乎不需要：
按最保守口径（所有文本都按 604px 最窄窗口算），译文需要超过 4 行的只有 **2/33023 = 0.01%**。
所以 MV 上**不加字号自适应**——避免过度设计。等真出现再按需加。

## 验收（不需要肉眼看窗口）

```bash
bash tools/mv-runtime/accept-layout.sh "<游戏目录>"
```

两步：① 探针报真实参数；② 插件在**真实游戏进程**里驱动真实窗口、真实字体、真实度量，
把逐行宽度算出来自己断言，结果以 JSON 落盘。

断言清单（当前 **11/11 通过**）：

| # | 断言 | 实测 |
|---|---|---|
| ① | 长文本确实被折行 | 72 字 → 折 2 处 |
| ① | 每行宽度 ≤ `contents.width` | 最宽 600 ≤ 604 |
| ① | **含最后一行**也 ≤ `contents.width` | 最后一行 552 |
| ② | 不丢字、不重字 | 72 → 72 |
| ③ | 行首禁则 | 3 行全部通过 |
| ③ | 行尾禁则 | 3 行全部通过 |
| ④ | 还原后一行都不折 | 1 行 |
| ④ | 还原后插入数为 0 | `wrapsInserted=0` |
| ④ | 开关可再次打开 | `enabled=true` |
| ⑤ | 折后行数 vs 可见行数 | 3 行 / 可见 4 行 → 放得下 |

> **★ 一个补掉的漏洞**：`processNewLine` 里记的逐行宽度只包含"以换行结尾"的行，
> **最后一行永远不被记录**（它后面没有换行符）—— 而最后一行同样可能溢出。
> 所以验收额外算了最后一行的宽度（= `drawTextEx` 的返回值）。

## 工具

| 文件 | 作用 |
|---|---|
| `tools/mv-runtime/run.mjs` | 通用加载器：**可逆**安装任意插件 → 跑游戏 → 收结果 → **逐字节校验还原** |
| `tools/mv-runtime/BB_Probe.js` | 运行时探针：报出 `contents.width`/`fontSize`/每字宽/每行字数等真实参数 |
| `tools/mv-runtime/BB_LayoutAccept.js` | 排版验收：在真实窗口里自检折行正确性 |
| `tools/mv-runtime/analyze-fit.mjs` | 离线分析：折行后**还剩多少放不下**（决定要不要做字号自适应） |
| `tools/mv-runtime/accept-layout.sh` | 一键验收总入口 |

`run.mjs` 的两条硬规矩：

1. **逐字节校验还原** —— 安装前备份 `plugins.js` 并记 SHA-256，跑完比对哈希，
   不一致就非 0 退出。"执行了还原"和"还原对了"是两件事。
2. **不改引擎文件** —— 只往 `www/js/plugins/` 放插件 + 在 `plugins.js` 末尾**字符串追加**一条注册
   （不 `JSON.parse/stringify` 重写整个文件，免得把游戏原有的注释和格式改掉）。
   跑完两者都恢复。`rpg_*.js` 自始至终一个字节不动。

## ★ 写运行时验收时踩到的两个坑（都值得单独记）

### 坑 1：**"0 项检查"被当成了"通过"**（最危险的一类假绿）

第一版验收在"等游戏就绪超时"时这样收尾：

```js
result.data = { checks: [], pass: 0, fail: 0 };   // ← 什么都没测
```

上层 runner 看到 `fail === 0` 就判"通过"。于是出现：
**验收根本没跑起来（超时 45 秒），却显示全绿。**

这正是最危险的一类假绿 —— 什么都没测，却给了绿灯。
修法两条：

1. 超时/异常**必须产出一条失败项**（`fail: 1`），不能留空数组；
2. `run()` 里捕获到的异常也要计入 `checks`，否则"抛异常 → 0 项检查"又是一次假绿。

> 教训：**"没有检查项"永远不等于"检查通过"。**
> 任何自动验收都要显式区分"通过 / 失败 / 未执行"三态，
> 绝不能让"未执行"落进"通过"。

### 坑 2：**游戏启动耗时波动极大**（2 秒 ~ 46 秒），定时窗口必须给足

同一个游戏、同一台机器，实测"到就绪"的耗时：

| 场景 | 耗时 |
|---|---|
| 探针单独跑（多次） | 2.0s / 6.2s / 6.5s |
| 探针 + BB_Layout | 27.8s |
| 排版验收（多次） | **40.1s** / 46.2s / 46.3s |

最初把就绪上限设成 45 秒 → **偶发超时**，于是给出假失败（有时又变成假绿，见坑 1）。
现在统一放宽到 **180 秒**（runner 默认 200 秒）。

原因不难理解：NW.js 是**多进程**（主进程 + 多个 renderer/GPU 进程），
这个游戏的 `www` 有 **3.4 GB** 资源、启用了 **140 多个插件**，
冷热缓存差别巨大。

> **这条对产品本身也重要**：加载器/注入器**不能假设"游戏启动很快"**。
> 反过来说，这也意味着"注入时机"要等就绪而不是等固定时长 ——
> 和 N1 看门狗那条经验是同一个道理（别赌时序）。
